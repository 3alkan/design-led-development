## Purpose and intended outcomes

Develop, maintain, explain, and distribute **Design-Led Development (DLD)** as one coherent, versioned software engineering methodology for humans collaborating with AI. The method itself is defined exclusively in [DLD Core](CORE.md).

The intended outcomes are:

- Humans and AI can adopt an identified DLD version and practice it using a minimal, self-contained project foundation.
- Contributors can evolve the methodology and its supporting materials without creating conflicting authorities or independently maintained Core variants.
- Users can distinguish methodology requirements, a project's approved design, optional explanatory guidance, and actual verification or release evidence.
- New and existing software projects can apply DLD incrementally, with clear human approval boundaries and continuity across AI sessions.

## Project scope and boundaries

The DLD development project owns the canonical Core source, its own project design and rules, the clean adopter starter, optional supporting reference material, and the local distribution assembly and validation script.

The project does not promise automatic design-to-implementation synchronization, a particular programming language or AI provider, a mandatory AI instruction file, or formal certification against an external engineering standard.

The methodology's normative behavior belongs in Core. This DESIGN specifies **the DLD product and development repository**, not additional rules for every adopting project.

## Product design

### One method and one canonical Core

[`foundation/CORE.md`](CORE.md) is the sole maintained authoritative source of the DLD methodology. Distribution copies MUST be derived from this source, never edited as competing method definitions.

For the v0.1.4 release candidate, Core declares **DLD Version 0.1.4** and **Methodology Version 0.1.4**. The repository's [VERSION](../VERSION) identifies the DLD Version and must match the corresponding Core declaration. Core owns the meanings and upgrade rules of both version identifiers; this project maintains and distributes them consistently.

### Two distributions from one source baseline

The project produces two distributions sharing the same versioned Core and DLD release identity:

| Distribution | Audience and contents |
| --- | --- |
| **Development** | DLD maintainers: canonical Core, this project's DESIGN and RULES, maintained optional supporting material and starter sources, with a local PowerShell packaging script. |
| **Product** | DLD adopters: a project-neutral starter containing the sole distributed Core copy, optional supporting reference material, version identity, changelog, and license. It excludes DLD development's own DESIGN, RULES, and internal packaging material. |

The product is assembled from an identifiable maintained source baseline using an explicit inclusion boundary and a versioned enclosing ZIP directory. Supporting materials are distributed but remain optional for adopting projects.

### Minimal adopter starter

The distributed starter contains exactly the minimum standardized foundation and records both adopted DLD Version and Methodology Version:

```text
README.md
foundation/
  CORE.md
  DESIGN.md
  RULES.md
```

Its `foundation/CORE.md` is generated byte-for-byte from the canonical Core. Its `DESIGN.md` begins as an explicitly unapproved project design template; its `RULES.md` records that no additional project-specific rules have been adopted. The README provides navigation and AI initialization guidance without becoming an independent authority.

Adopters copy the starter into their own projects, then develop their own designs and approved rules. They do not inherit the DLD development project's approvals or constraints. The starter alone is sufficient to apply the adopted DLD methodology without supplemental documentation, network access, or DLD repository access.

### Licensing boundaries

The canonical Core, supporting materials, and DLD development documentation are GPLv3-covered under [`LICENSE`](../LICENSE). The three maintained, project-customizable starter templates (`starter/README.md`, `starter/foundation/DESIGN.md`, and `starter/foundation/RULES.md`) are CC0-1.0 under [`LICENSE-CC0`](../LICENSE-CC0), allowing unrestricted reuse by adopting projects. The generated Core copy retains its GPLv3 licensing; adopting DLD does not impose a license on independently created project work.

### Optional supporting documentation

The product provides one optional supporting reference on adopting-project repository organization, maintained at [`docs/supporting/repository-layout.md`](../docs/supporting/repository-layout.md). Packaging places it at `supporting/repository-layout.md`. Adopters MAY copy it into their own `docs/dld/` directory. Additional supporting material is introduced only when useful; none may add methodological obligations beyond Core.

## Development and release approach

DLD development is governed by the canonical Core and this project's approved design and rules. The project's starter and supporting artifacts must not contradict the Core or independently establish methodological requirements.

The local [packaging script](../scripts/package.ps1) assembles the product using PowerShell 7 without third-party dependencies. It must ensure that distributed Core bytes match the canonical source, that the DLD Version and Methodology Version are correctly propagated, that only intended product materials are included, and that the generated ZIP and checksum are consistent and reproducible in a supported environment. It must preserve the previous successful outputs when preparation fails and restrict generated-file operations to `build/`. The script owns the procedural details of file mapping, validation, archiving, and recovery.

Before publication, release metadata and distribution contents must reflect the intended source baseline. Verification evidence and limitations must be reported accurately. Design approval, a successful package build, authorization to merge, and authorization to publish are distinct events.

## Acceptance criteria

- Exactly one canonical maintained Core defines DLD; every distributed Core copy matches it byte-for-byte.
- The project foundation and its approval history remain distinguishable from the templates given to adopters.
- The minimal starter works with only its README, Core, draft DESIGN, and rules-empty RULES; no optional document or AI-specific file is required for compliance.
- Both distributions use the same DLD Version and source baseline, carry the correct Methodology Version, include only their intended audience-specific materials, and preserve valid relative links.
- The supporting reference can be copied into `docs/dld/` beside the starter without broken relative links or a second methodological authority.
- The canonical Core, supporting reference, starter, and package behavior do not contradict one another.
- ZIP creation is repeatable for identical inputs and packaging environments; unsuccessful builds do not knowingly replace valid outputs, and all filesystem writes remain confined to `build/`.
- Validation reports actual checks and limitations rather than inferring broad correctness from a successful build.
- Releases reflect explicit human authorization and truthful version, approval, changelog, and evidence records.
